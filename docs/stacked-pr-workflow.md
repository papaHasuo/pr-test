# Stacked PR運用ガイド

## 目的

Epicから層ごとのPRを作成し、AIが実装と一次レビューを進めながら、
人間が小さな差分単位で最終レビューできるようにする。

AIレビューの完了は人間レビューの代替ではない。AIは次層の実装を先行させるために
活用し、人間はstackの下位PRから順に設計と実装の妥当性を判断する。

## 基本フロー

各層で次の手順を繰り返す。

1. 対象層のIssue、受け入れ条件、依存する下位層を確認する。
2. 対象層を実装し、対象層に対応するテストを追加する。
3. 対象層の変更とテストをAIレビューする。
4. AIレビュー結果をPRコメントへ記録する。
5. Blocking指摘を修正し、必要ならAIレビューを再実行する。
6. 人間確認事項をPRコメントへ記録する。
7. 次層へ進める条件を満たしたら、人間の最終判断を待たずに次層の実装を開始する。

各PRでは、少なくとも次の3項目を明記する。

- AIレビュー結果
- 人間レビューで確認したい事項
- 次層への進行可否

## 指摘の分類

AIレビューの指摘は、次の2種類に分類する。

### Blocking

修正が完了するまで、次層の実装を開始してはいけない。

- コンパイルエラーやテスト失敗
- 受け入れ条件を満たさない実装
- データ破壊や認証欠落など、明らかな重大問題
- 下位層との契約が成立していない問題

### 人間レビューで確認

次層へ進めてよいが、人間の判断が必要な事項としてPRに残す。

- 責務分割や命名の設計判断
- 複数の妥当な実装方針の選択
- テストの粒度や将来の拡張性
- 今回の受け入れ条件には含まれない改善提案

指摘がない場合も、PRコメントに「Blockingなし」と明記する。

## PRコメントのテンプレート

```text
## AIレビュー結果

### Blocking
- なし

### 人間レビューで確認したい事項
- なし

### 修正内容
- 完了フォームの表示条件をIN_PROGRESSにも対応
- UI統合テストを追加

### 次層への進行
- Controller層の実装を開始してよい
```

人間レビューで確認したい事項がある場合は、次層へ進める場合でも
「人間レビュー待ち」と明記する。人間の確認を受けた後に、必要であれば
PRコメントを更新する。

## 下位層を変更した場合のrebase

後続PRを作成済みでも、下位PRの変更内容によって対応を分ける。

| 変更内容 | 後続PRの対応 |
| --- | --- |
| 下位層の内部実装だけを変更 | 原則として対応不要 |
| メソッド名、引数、戻り値、例外を変更 | 後続ブランチをrebaseし、影響箇所を修正 |
| 画面、HTTP、Repositoryなどの契約を変更 | 後続ブランチをrebaseし、関連テストとAIレビューを再実行 |
| コンフリクトが発生 | 下位層の契約を優先して解決し、後続層の差分を最小限修正 |

rebase後は、少なくとも次を実行する。

1. 影響を受ける層のテスト
2. 後続PRのテスト
3. `./mvnw test`
4. rebaseによる変更範囲のAIレビュー

rebaseで仕様や契約が変わった場合は、PR本文に変更理由と影響範囲を記載する。

## 人間レビューとマージ

次層の実装開始と、下位PRのマージは別の判断として扱う。

- AIレビュー完了後は、Blockingがなければ次層の実装を開始してよい
- 下位PRは人間レビューが完了するまでマージしない
- マージはstackの下位PRから順に行う
- 下位PRのマージ後、GitHubまたはstack管理ツールによるbase変更を確認する
- 後続PRの差分が想定どおりか確認してから、次のPRをレビューする

これにより、AIは実装を先行でき、人間は小さなレビュー単位を維持できる。

## EpicとSub-Issueの使い分け

Epicには、全体の目的、層の順序、依存関係、各Sub-Issueの概要を記載する。
Sub-Issueには、担当層、実装範囲、対象外、受け入れ条件、実施するテストを記載する。

AIレビューの結果や実際の修正内容は、Epicではなく各PRに記録する。
Epicの受け入れ条件を変更する場合だけ、Epicと関連するSub-Issueの両方を更新する。
